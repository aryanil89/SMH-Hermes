# Third review — measurements, not opinions (2026-08-04)

A data-science pass over `gpt_model_feedback.txt` (raw GPT-authored feedback) and
`FEEDBACK_RESPONSE_2026-08-04.md` (this project's response to it) — both since removed as
superseded internal working drafts once their conclusions were folded into
[POSITIONING.md](POSITIONING.md) and the fixes below. This document exists because **neither
measured the system it was giving advice about**. Everything below was measured this session,
with the command that produced it.

**The headline.** Our simulated telemetry reported at least one CRITICAL subsystem on **68.7% of
calls**, and only **19.3%** of calls were all-clear. The centrepiece of both improvement plans —
"temperature rose, then storage degraded, therefore cooling problem" — was competing against a
**35.2%** chance that two subsystems fire together by coincidence. That has been fixed (§2), and
the fix is now guarded by a test.

## 1. Verdicts on the two prior documents

### `gpt_model_feedback.txt` — excellent positioning, unsound numbers, fabricated citations

**Adopt nearly verbatim:** §1–4 (reposition to on-device incident triage), §9–10 (demo story
shape), §16–21 (governance, component naming, architecture wording), §26–29 (audience framing, title,
one-liner). This is the highest-value, zero-code change available and it is right.

The single sharpest idea in the document is **§25 Scenario 4 — workload spike that is *not* an
incident**. That is a negative control, and it is the thing that proves judgement rather than
pattern-matching. Keep it.

**Reject the numbers**, for the reasons FEEDBACK_RESPONSE already gave (additive double-counting;
`81%` confidence with no calibration set; a 30-minute forecast with no model). Concur fully.

⚠️ **Citations are fabricated.** The document cites `aihub.qualcomm.com/geniex` four times as the
source for statements about *this repository* — its README, its architecture, its 2–4 minute
latency. That URL was fetched during this review: it is Qualcomm's GenieX product page and contains
nothing about Hermes, Arduino, Telegram, or MCP. The *claims* are accurate, because they came from
pasted context — but the evidence is decorative. **Never copy those citation markers into the
submission**, and treat any factual claim in that document as unsourced until checked here.

### `FEEDBACK_RESPONSE_2026-08-04.md` — correct diagnosis, three defects

**Stands, and should drive the work:** P1 (the latency budget forbids LLM-computed scoring — compute
in TypeScript, let the model narrate), P3b (refuse percentage confidence without a calibration set),
P4 (label the forecast as an extrapolation with stated assumptions), and especially **§3 —
confidence collapses when data is stale.** That last one is the strongest trust idea anyone has
proposed for this project and it is nearly free.

Three defects:

**(a) It did not measure the base rate.** See §2. Its P2 fix (couple the simulators) is necessary
but was not sufficient on its own: with a 35.2% coincidence floor, real coupling would have been
statistically invisible.

**(b) P2 and P3a contradict each other.** P2 says *couple storage latency to temperature*. P3a says
*score by independent signal family*. If storage is a deterministic function of temperature, then
"temperature and storage agree" is true **by construction** — it is one signal counted twice, which
is exactly the double-counting P3a set out to prevent. Confidence would be highest precisely where
the evidence is most redundant. Fix in §3 below.

**(c) "§14 timeline is cheap — we already log timestamped events" is wrong for telemetry.** True for
the UNO Q sensor log. False for storage/network/compute: those generators are **stateless**, seeded
per call, and keep no history at all. A timeline of "09:04 storage latency increased" cannot be
produced from them without adding persistence. That item is not free; price it before promising it.

## 2. Measurement: the simulators were crying wolf

Method: 20,000 seeded reports per generator, counting `overallStatus === "critical"`.

```powershell
cd mcp-tools
node -e "const n=require('./dist/mock/network.js'),s=require('./dist/mock/storage.js'),c=require('./dist/mock/compute.js'); /* count over 20k seeds */"
```

| | Before | After | |
|---|---|---|---|
| network CRITICAL | 44.2% | **3.6%** | |
| storage CRITICAL | 26.1% | **3.8%** | |
| compute CRITICAL | 48.1% | **4.3%** | |
| **any subsystem CRITICAL** | **68.7%** | **8.5%** | 8× fewer |
| **≥2 families CRITICAL at once** | **35.2%** | **2.6%** | the coincidence floor, 13× lower |
| **all three OK** | **19.3%** | **88.3%** | a healthy baseline is now showable |

**Root cause.** Each generator drew its incident chance independently *per entity* — `chance(rng,
0.15)` across 5 links, 4 volumes, 6 nodes — and a "stressed" entity lands in critical territory
roughly 60–73% of the time. Compounded over entities and then over three subsystems, almost every
call surfaced something red.

**What it invalidated.** GPT's §9 Step 1 ("Rack B1 status: Healthy… Risk: Low") would have failed
~81% of the time on stage. Any correlated-incident narrative was competing with a coin-flip-ish
coincidence rate. And any "N of M families agree" confidence metric inherits that floor.

**The fix.** Incidence recalibrated (`DEGRADED_LINK_P`, `STRESSED_VOLUME_P`, `STRESSED_NODE_P` in
`src/mock/*.ts`), with the *shape* of the distributions untouched — a stressed entity still looks
stressed. Baseline health is now the normal state and incidents are injected deliberately, which
matches how the demo actually works. Pinned by
[`src/mock/base-rate.test.ts`](../mcp-tools/src/mock/base-rate.test.ts) so it cannot silently
regress.

**Second fix — reproducibility.** `createRng()` previously fell back to `Date.now() ^ Math.random()`,
so a reviewer asking the same question twice got different telemetry, and two tool calls inside one
agent turn could contradict each other. It now derives the seed from a **time window** (default 60s,
`SIM_WORLD_WINDOW_S`): the simulated datacenter holds still long enough to be interrogated, then
moves on. Explicit seeds are unchanged, so tests are unaffected.

## 3. The real sensor has the opposite problem: it never fires

484 logged samples from the UNO Q:

| | min | median | max | over warning threshold |
|---|---|---|---|---|
| temperature | 22.8 °C | 25.3 °C | 28.9 °C | **0.0%** (warning is 30 °C) |
| humidity | 52.2 % | 62.0 % | 72.6 % | 0.2% (warning is 70 %) |

**The real sensor has never once crossed its own alert threshold.** Every CRITICAL environmental
alert observed so far — 33.88 °C, 38.95 °C — was *mock* data produced while the board was offline.

Consequences to act on:

1. **The thermal demo beat is unrehearsed and unproven.** It requires physically pushing the sensor
   from ~25 °C past 30 °C (hand, breath, a warm mug). Max ever recorded is 28.9 °C. **Test how long
   this takes before it is on the run sheet**, and have button C as the fallback trigger.
2. **Consider ASHRAE-grounded thresholds.** 18–27 °C is the recommended envelope, so a 30 °C
   warning is defensible — but say *why* it is 30, not just that it is.
3. The asymmetry is itself the honesty story: the *simulated* subsystems were noisy and the *real*
   one is quiet. That is the right way round now, and it is worth a sentence on stage.

## 4. Fixing the independence contradiction

The other session is implementing thermal coupling as this is written, and has made the right
structural choice already: **only `zone-east` is thermally affected; `zone-west` runs the same
simulator as a control.** That is a discriminative design, not just a correlated one.

Build the confidence metric on that property, not on agreement:

- ❌ **Wrong:** "temperature is high AND storage latency is high → 2 families agree → high
  confidence." Under coupling, storage *must* rise when temperature does. This measures nothing.
- ✅ **Right:** "the affected zone degraded **and the control zone did not**, **and** network shows
  no packet loss — the pattern matches the thermal signature and mismatches the network signature."
  That is evidence, because it could have come out otherwise.

Rule of thumb for the scorer: **a derived signal never counts as an independent family.** Count
*families* (physical / storage / network / compute), count a coupled pair once, and score
confidence from **pattern discrimination** — which hypotheses the evidence rules *out*.

## 5. What I would add that neither review proposed: an evaluation harness

Both documents argue about what the triage engine should output. Neither proposes measuring whether
it is *right*. A rule-based engine can still be evaluated, and this is the cheapest credibility
available:

1. Generate N seeded scenarios with **known ground truth**: thermal incident, network incident,
   workload spike (the negative control), nothing-wrong.
2. Run the triage logic over each.
3. Report a confusion matrix and per-class accuracy.

That yields a sentence no other team will have — *"across 200 seeded scenarios the triage engine
attributes root cause correctly in X%, including Y/Z on the workload-spike negative control"* — and
it is ordinary `vitest` using the seeding that already exists. It would also have caught the
base-rate defect in §2 automatically, before a stage did.

This is the highest-value remaining item on the data-science side, and it is worth more to the
Technical Implementation score than another feature.

## 6. On the latency argument that drives everything

FEEDBACK_RESPONSE's P1 — the reason to compute verdicts in TypeScript rather than in the model — is
correct and should be followed. But note what it rests on: **~15–16 tok/s from a single essay
timing.** [BENCHMARKS.md](BENCHMARKS.md) §1 (throughput of the *served* Q4_0 artifact, pp/tg split,
≥5 reps) is explicitly **not run**. The §3 per-op work that *was* done characterises the W4A16
bundle, which is not what serves the agent.

Two implications:

- Do §1 before quoting a throughput number to an audience. The claim is load-bearing for the demo design.
- **A richer tool output costs prefill.** Every agent iteration re-prefills the whole conversation
  (`cache_prompt` honoured ~18%), so a verbose evidence-pack JSON directly slows the turn it is
  meant to speed up. Cap the tool payload and measure the delta. BENCHMARKS Table 1 shows decode
  cost roughly doubling from cl512 to cl4096 on the bundle — context length is not free.
