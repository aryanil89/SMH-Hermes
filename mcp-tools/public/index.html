Executive overview · Snapdragon Multiverse Hackathon 2026

Hermes: On-Device AI Operations Engineer

Hermes is an AI operations engineer that runs entirely on a Snapdragon X Elite — no cloud AI, no data leaving the laptop. It correlates real physical sensor signals with infrastructure telemetry to tell an on-call engineer what is wrong, why it matters, and what to do next.

What Hermes is

A local reasoning layer over signals an ops team already has. It correlates, prioritises, explains and recommends — and it reasons about who is physically at the rack, asking a human before anything proceeds.

What Hermes is not

A replacement for monitoring, DCIM or sensors. Datacenters already have those. Hermes does not collect the signals — it judges them.

The offline claim

The intelligence is offline: the model, the reasoning, the tool calls and the sensor path all run on the Snapdragon — provable by cutting the WiFi mid-demo. The one internet hop is the phone notification, a message relay, not intelligence, and a swappable adapter — Slack, Teams, Discord, WhatsApp and Signal share the same gateway; we demo on Telegram.

Disclosure

Network, storage and compute telemetry are simulated with realistic data patterns; the environmental path is live from an Arduino UNO Q. The MCP adapters are the seam — the same tools can be pointed at real DCIM/BMS/SNMP without touching the reasoning layer.

Conceptual architecture · what the parts are

Three devices, one pipeline

Everything inside the laptop survives a WiFi cut. Telegram — and only Telegram — needs the internet, and it carries chat text, never the authorisation to open a door.

Arduino UNO Q

sensing

Samples temperature, humidity, ToF distance and button state over I2C, and pushes a periodic climate tick (~10s) plus edge-triggered button and presence events to the laptop over its WiFi + Tailscale link. It has no RTC battery, so every cold boot needs its clock set before its data is trusted. USB-C is used only to flash and configure the board — it carries no sensor traffic.

Components on this device

  • Modulino Thermo — temperature + humidity, Qwiic/I2C
  • Modulino Distance — ToF mm, presence gate at 1000mm; the only physical-security signal in the system
  • Modulino Buttons — A / B / C, both-edge events
  • STM32 sketch.ino — reads the bus, bridges to the Linux side
  • main.py — App Lab container, writes sensor_log.jsonl
  • push_sensor_log.sh — scp's the log to the laptop over Tailscale every 10s
Sends to
Laptop, via WiFi + Tailscale VPN
Receives
Nothing — one-way telemetry

Snapdragon X Elite laptop

reasoning

Ingests the sensor log; runs four MCP tool servers (environmental is real, network / storage / compute are realistic mocks) that the Hermes Agent calls over stdio; sends tool-augmented prompts to a local Qwen3-4B model served by GenieX on the Hexagon NPU; runs a 15-second watchdog loop for proactive paging; and serves the wall display and the access terminal, both from one Node process on port 7788.

Components on this device

  • environmental / network / storage / compute servers — MCP tools, stdio
  • Hermes Agent — MCP client, skills, memory, cron
  • Watchdog loop — 15s tick, health on 127.0.0.1:7789
  • GenieX serve — OpenAI-compatible endpoint, 127.0.0.1:18181
  • Qwen3-4B-Instruct-2507 — GGUF Q4_0, 64K context
  • Hexagon NPU v73 — CPU stays at 12–17% during inference
  • Wall + access terminal server — 127.0.0.1:7788, SSE every 2s

Why the authorisation layer sits below notification

Telegram carries the question and the page; it never carries the answer. A physical access decision is made on the phone's local page over the tailnet, straight to the laptop — not through a third-party relay. Approvals are the one write path in the system; everything else here is read-only telemetry.

Logical architecture · what moves

From a bus read to a page on the phone

One tick of information, end to end. Each stage may only use what the stage before it produced, and only two stages are allowed to act on the world: the one that pages the on-call, and the one that asks a human about a stranger at the rack.

  1. 1 · Acquire

    Physical signal → log line

    • I2C sample: thermo, ToF distance, button edges
    • sketch.ino → main.py appends sensor_log.jsonl
    • scp to the laptop over Tailscale, every 10s

    carries climate tick ~10s · edge events on change

  2. 2 · Ingest

    Log line → trusted reading

    • sensor-log.ts tails the file: size, lines, newest timestamp
    • Freshness gate UNOQ_LOG_MAX_AGE_S decides real vs stale
    • Stale or unreadable → mock reading, labelled as mock

    carries one EnvironmentalResult + its provenance

  3. 3 · Derive

    Events → state

    • Paired edges → door / lighting / presence; newest edge wins
    • No edge in the window → unknown, never "closed"
    • Network / storage / compute drawn from a 60s seeded world

    carries channel states · climate trend · four families

  4. 4 · Correlate

    State → verdict

    • assessIncident() — the call behind get_incident_assessment
    • Risk index /100, confidence, evidence, likely cause, action
    • One tick = one world seed, so no panel disagrees with another

    carries an assessment every side of the system shares

  5. 5 · Decide

    Verdict → who is told

    • Alerting, access and conversation branch here
    • Only these paths may write or send anything
    • Every send records whether it was actually delivered

    carries a page, a challenge, a reply — or deliberate silence

  6. 6 · Surface

    Everything → one frame

    • snapshot.ts assembles one DashboardSnapshot per 2s tick
    • SSE /api/stream → this wall, rendered as a keyed diff
    • gateway-bridge.ts mirrors the phone thread, both directions

    carries the wall · the phone terminal · /api/state

Alerting path

may stay silent
  1. decideAlert() — threshold crossing, cooldown, escalation
  2. suppress.ts reads .state/access.json
  3. Verdict expected → the page is held, not cancelled
  4. Watchdog loop every 15s writes environmental-watch.json
  5. Telegram send · the wall mirrors the state file after the fact

Held pages fire the moment the responder leaves, annotated as held. A stale access.json fails open and pages anyway — a watchdog silenced by a dead input is indistinguishable from one silenced by good news.

Access path

needs a human
  1. Presence edge (ToF < 1000mm) → AccessSentry.update()
  2. identify.ts — detection only, so everyone reads unknown
  3. decide.ts → clear · expected · challenge · tailgating…
  4. notify.ts pushes the challenge to the phone (text only)
  5. Approve/deny on phone.html — tailnet, never Telegram
  6. Append-only audit entry in .state/access.json

The image is resolved and dropped; nothing on this path writes image bytes to disk. A decision relaxes the severity but never rewrites the finding.

Conversational path

on demand
  1. Question typed on the phone → Telegram Bot API
  2. hermes gateway long-polls it — sole consumer of the token
  3. Hermes Agent calls the MCP tools over stdio
  4. GenieX → Qwen3-4B on the Hexagon NPU, 127.0.0.1:18181
  5. Reply back over Telegram to the phone
  6. The wall reads the transcript read-only and shows both sides

The same tool functions answer the agent and this display, so the wall and the phone cannot contradict each other about what the rack is doing.

What crosses the internet

Telegram text only: the question, the reply, the page, the challenge notice. Never an approval, never an image, never a sensor stream. Cut the WiFi and every stage above still runs — only the notification hop stops.

What persists

sensor_log.jsonl (append-only) · environmental-watch.json (watchdog) · access.json (challenge + audit) · roster.json (embeddings, never images). One writer per file.

What is real

Environmental and access are live from the board. Network, storage and compute are simulated with realistic patterns and every card says so. The MCP adapters are the seam where real DCIM/BMS/SNMP would replace them.
